Lucid CV demo résumé: three variants compared

Three variants of the Lucid CV demo résumé (one column on two pages, one column on one page, two columns on one page) were built fresh and read back by seventeen text-extraction engines, simulating the process that an applicant tracking system (ATS) uses before parsing a CV. Four of the engines read the PDF’s tags instead of the page, as screen readers do. All three variants pass every test: every engine expected to handle the layout returns every phrase, in order, with ordinary spaces between words, and every file is valid PDF/A-2B and PDF/UA-1. The only shortfalls come from engines with known limitations: three that cannot separate two columns lose about a third of the two-column variant’s phrases, and OCR misreads 1–5 phrases per variant.

Introduction

The three variants

All three variants present the same fictional Senior Software Engineer résumé shipped with the template in resources/demos/. The number before c is the number of columns and the number before p the number of pages, so 1c1p is one column on one page. 1c2p is the full text, identical to the template’s sample contents.tex, whereas the one-page variants are condensed versions of it.

A phrase is one piece of text that must survive extraction intact: a heading, an entry, a bullet, a contact field. Each variant is checked against its own phrases.

How the résumé is read back

Before an ATS can recognize a name, a job title or a date, it has to pull the text out of the PDF, and extraction software differs in how it does that. Every PDF is therefore read by seventeen engines: the libraries behind common PDF viewers and Linux tools (poppler, MuPDF, PDFium, pdf.js, Ghostscript), Python and Java document pipelines (pdfminer, PDFBox, Tika, iText), several in more than one mode, and Tesseract, an OCR engine that reads the rendered page like a scanner.

Four of them, marked -struct, read the PDF differently. A tagged PDF carries a hidden outline (its tags) that marks the document’s elements and defines its reading order. Most engines ignore it and infer the order from where text is drawn on the page; poppler-struct, pdfjs-struct, tika-struct and itext-struct follow the outline instead, as screen readers and tag-aware parsers do. They therefore test the tagging itself: untagged text never reaches them, and decorative elements such as icons and dotted leaders are skipped.

Strict and advisory engines

Each engine is either strict or advisory for a given layout.

  • A strict engine is expected to read the layout perfectly; missing or scrambling even one phrase fails the test.
  • An advisory engine has a known limitation no résumé can fix; its results are reported but never fail a test.

Tesseract is advisory everywhere: it reads pixels, not the PDF’s text, so its errors measure the OCR rather than the document. In two columns, the engines that rebuild lines across the full page width merge the columns, so they are advisory there, and two engines that sort text by position are advisory for reading order only. The four tag readers are strict everywhere: they never look at where text is drawn, so the layout cannot affect them. In one column, every engine except Tesseract is strict.

6 · XMP metadata

What it tests. A PDF stores its title, author, subject and keywords twice: in a legacy dictionary that most viewers display, and in an XMP packet that PDF/A and PDF/UA require. A gap between the two goes unnoticed in a viewer, so the test checks that every field reached the XMP with the same value, that its language matches the document’s, and that viewers show the title rather than the file name.

7 · Hidden text

What it tests. Hidden (visually invisible) text is a common method for keyword stuffing, i.e., including keywords beyond the visible text to increase search engine ranking. It is often achieved by placing white words on white background, tiny font sizes, or pusing the text off the page. Some screening tools already detect and flag the whole document, discarding the candidate with such a resume from the process entirely. This test checks that every character other than whitespace is visible: drawn, in a colour distinguishable from white, opaque, at least 4 pt, on the page, and not hidden under other text or an image.

Two-column splicing in 2c1p

The three engines that lose phrases in 2c1p rebuild each printed line across the full page width, so a phrase that wraps in one column gets the other column’s text inserted where it breaks. Accordingly, the missing phrases are the long, wrapping ones, spread over every section.

Discussion: two columns. Every strict engine returns every phrase in all three variants, so the text stored in the PDF is complete whatever the layout. The only difference comes from two columns: in 2c1p, poppler-layout, ghostscript and pdfbox-sorted recover only 67–71% of the phrases. This is not a fault in the PDF: these engines cannot separate side-by-side columns, and they return 100% of both one-column variants. The compressed style causes no losses.

Discussion: the tag readers. All four return every phrase in every variant, which also confirms that every visible phrase is tagged. Ignoring the page layout, they read 2c1p as cleanly as a one-column résumé.

Discussion: Tesseract OCR. Tesseract reads a rendered image of the page, not the stored text, so its misses are mostly character errors. The phone number fails everywhere because OCR drops the narrow gaps between its digit groups; the rest are scattered misreads, mostly a capital I taken for l. In 2c1p, the education date wraps after its dash and OCR splits the halves into separate blocks. Rendering at 600 dpi does not help: 8 / 3 / 7 misses against 5 / 1 / 3 at 300 dpi, with new misreads such as net/htto.

Possible fix. The I/l errors have one cause: in the Inter font, the capital I and the lowercase l are both a plain vertical stroke, so OCR has to guess. The fix is a body typeface whose capital I and lowercase l differ in their regular shapes, for example an I with serifs or an l with a tail. The wrapped date in 2c1p could be kept on one line by shortening the entry or widening the left column.

Practical relevance. In practice, the OCR errors matter little. ATS parsers work primarily with the text stored in the PDF, and since this file is tagged, PDF/A-2B- and PDF/UA-1-compliant and its text reads back completely, a fallback to pure OCR is unlikely. The OCR results are therefore for informational purposes only.

9 · Reading order

What it tests. Finding every phrase is not enough if they come back scrambled: an ATS that reads a date after the wrong employer files it under the wrong job. The test scores how much of each engine’s output keeps the order the text is stored in, from 0 to 1 (perfect). The tag readers are scored against the order the tags declare instead, which in turn must match the stored order. The body must score 1.00 in every strict engine; the contact header is only reported, since the order of contact fields carries no meaning.

The stored order comes from poppler-raw, which outputs the text exactly as stored. poppler in 1c1p: the second contact line comes first. poppler outputs linkedin.com/in/… and github.com/…, the second contact line, before US citizenship and adriancastellanos.dev, the end of the first. Every field is complete, only in a different order. Since this is a header and the text is not garbled, this does not affect ATS performance.

Discussion. In both one-column variants every engine returns the body in document order, so order is a problem only in two columns. There, the eleven engines that output text as stored or as tagged keep a perfect 1.00: the seven that output the stored text (poppler-raw, mupdf, pdfium, both pdf.js builds, pdfbox, tika) because the template stores each column as one continuous block, and the four tag readers because the tags declare that same order. The engines that re-sort text by position depart from it to different degrees: pdfminer still reaches 1.00, poppler moves one block (0.95), and the three side-by-side engines also scramble what they recover (0.55–0.57).

Two columns on one page. The tags and the stored text agree in 2c1p because it fits on one page. In a two-column résumé that runs on to a second page, the tags finish the column that continues before starting the other, while the stored text, pdf.js and Tika take page 1 and then page 2; the test holds the tag readers strictly and fails such a document. A two-column résumé is meant to fit on one page.

  • Passed in all three variants: every test. Real word spaces, icons, PDF/A-2B, PDF/UA-1, metadata, no hidden text, and phrase extraction and body order in every strict engine. Every engine returns plain U+0020 word gaps.
  • One column reads back perfectly. In both one-column variants, compressed or not, all sixteen text-reading engines return every phrase with the body in order. The only deviation is cosmetic: poppler lists the second contact line first in the compressed variant’s header, which is reported but never fails.
  • The tagging holds up. The four engines that read the tags instead of the page return every phrase of every variant in order, two columns included: the résumé reads the same to a screen reader or tag-aware parser as it looks.
  • Two columns is the only layout with real extraction issues. Three engines merge the columns and recover only 60–63 of 89 phrases. They and poppler also reorder the body. An ATS using one of them would receive merged columns, yet the PDF is sound: the eleven engines that keep the stored or tagged order read it perfectly.
  • OCR errors do not depend on the layout or resolution. Tesseract misreads the same few characters in one and two columns, and more of them at 600 dpi than at 300.
  • Recommendation: where the ATS is unknown, submit a one-column variant. Keep two columns for human readers or systems known to keep the stored or tagged text order, and keep a two-column résumé to one page.

Limits

  • Order is measured against the stored order (read by poppler-raw, which therefore always scores 1.00). However, this order is cross-checked against the tags produced by itext-struct.
  • Hosted commercial parsers cannot be measured locally. Each runs a similar or one of engines, before its own analysis.

Reproduce

From tests/, one command per variant:

1c2p./pipeline.sh ../resources/demos/1c2p/main.tex
1c1p./pipeline.sh ../resources/demos/1c1p/main.tex
2c1p./pipeline.sh ../resources/demos/2c1p/main.tex

Each run generates phrases.txt, builds <label>.pdf, runs run.sh and writes run.log and pipeline.json to tests/out/<variant>/. The 600 dpi pass renders each built PDF with pdftoppm -r 600 -gray -png, runs tesseract on every page, and scores the output with the same check.py and order.py.
